# 运维手册

## 1. 接入

```bash
ssh huangxb@172.1.14.12          # 免密已配
echo <sudo密码> | sudo -S <命令>  # 非交互 sudo；密码不写在文档里，见密码本
```

> **绝不能 `systemctl restart ttyd`** —— 它的 `KillMode=control-group` 会连带杀掉里面常年挂着的 screen 会话。

## 2. 各服务的重启方式（改代码后）

| 类型 | 命令 | 注意 |
|---|---|---|
| PMS 后端 | `sudo systemctl restart pms.service` | 改后端 py 必须重启 |
| PMS 前端 | `bash -lc "cd ~/pms/frontend && npm run build"` | **不用重启服务**，Flask 直接吐 dist；npm 不在非交互 PATH，必须 `bash -lc` |
| 宿主 Python 服务 | `sudo systemctl restart paddle-ocr ocr-multi okf-kb` | — |
| compose 容器 | `cd ~/platform && docker compose build <名> && docker compose up -d <名>` | **只 restart 不换镜像层** |
| agent 盒子 | `bash /tmp/deploy_box.sh …`（内部 `rm -f` + `run`） | 同上 |

> **最常踩的坑**：改了代码 `docker restart`，然后发现没生效——容器绑定的是创建时的镜像 ID，必须重建容器。

## 3. 备份

改动前的习惯做法（本项目一直这么干）：

```bash
cp app.py app.py.bak.<改动名>          # 代码
cp ~/pms/pms.db /tmp/pms.db.bak.<日期>  # 数据库
```

现有备份后缀示例：`.bak.agentauth`、`.bak.agents`、`.bak.niuma`、`.bak.theme`、`.bak.captcha`、`.bak.vlex`。

## 4. 日常巡检

```bash
# 一眼看全（内网总台）
curl -s 127.0.0.1:9099/api/status | python3 -m json.tool | head -40

# 分层看
systemctl is-active pms paddle-ocr ocr-multi okf-kb bge-m3 ops-console
docker ps --format '{{.Names}}\t{{.Status}}'
nvidia-smi --query-gpu=name,memory.used,utilization.gpu --format=csv
uptime                                   # load 长期 20+ 是 ccgp 在跑，正常
```

## 5. 排障速查

| 症状 | 查什么 |
|---|---|
| 网页终端刷屏乱码 | 鼠标追踪模式残留，`screen -S pms -X stuff '^U^Creset\015'`，**别重启 ttyd** |
| OCR 很慢 | ccgp 在抢 CPU，看 `systemctl show ccgp@ocr -p CPUQuotaPerSecUSec` |
| OCR 500 显存错 | `nvidia-smi` 看占用，确认没有第二份 VL 模型被加载 |
| agent 报 PMS 401 | `PMS_AGENT_USER` 与密码文件是否匹配；账号是否在免滑块白名单 |
| agent 流式报错 | llm-gateway 的 SSE 补丁是否还在（容器被 recreate 会丢） |
| LLM 调用不计费 | 是不是绕过了 llm-gateway 直连模型厂商 |
| 归档分类不准 | 看 `/extract` 返回的 `source`：是不是误走了「pdf文本直取」只拿到水印 |
| **公网全站 Error 1033** | Clash TUN 劫持了 cloudflared。`journalctl -u cloudflared-pms` 看 `ip=` 字段，出现 `198.18.0.x` 就是 fake-ip，见第 8 节 |
| **服务 active 但功能不通** | `is-active` 报 active 也可能是崩溃循环。`systemctl show <svc> -p NRestarts --value` 不为 0 就去看 journal |
| bge-m3 起不来 | 3070Ti 显存被 PaddleOCR-VL 占满。`nvidia-smi` 看剩余，不够就让 bge 走 CPU（drop-in `zz-nogpu.conf`） |

## 6. 关机与重启

所有监听端口的服务都已 systemd `enabled`，24 个容器 `restart=unless-stopped`，开机自恢复。

> **2026-08-14 更正**：这句话以前不完全成立。OPMS(9100) 当时是手工起的，每次重启都得记得拉；
> 现已补成 `opms.service`（见 opms 仓库 `deploy/README-systemd.md`）。
> 目前**仍需手工起的只剩 PMS-dev(1574)**，它与生产 1573 共用同一份代码和同一个 `pms.db`，
> 常驻两个进程写同一个 SQLite 不安全，故**刻意不开机自启**，要用时手工起：
> `cd ~/pms/backend && PMS_PORT=1574 ../venv/bin/python app.py`
>
> 另注意：**重启后所有人都会被登出**。PMS 是 30 分钟滑动空闲过期，机器关着那段时间没有请求刷新，
> 回来就会被弹到 `/login?expired=1`。这是预期行为，不是故障。

`ccgp` 是唯一没有端口所以扫端口会漏的，已收编为模板单元 `ccgp@.service`，6 个实例均 enabled。

## 8. 公网入口（cloudflared）与 Clash 的相互干扰

`cloudflared-pms.service` 单隧道跑全部域名（pms/rag/term/cg/ops/根域），配置 `~/.cloudflared/config.yml`。
**这台机器同时跑着 Clash Verge 的 TUN（网卡 `Meta`，gvisor 栈，`dns-hijack: any:53`），两者会打架。**

**症状**：公网全站 Cloudflare **Error 1033**，而 systemd 报 `active`，日志无限刷
`Unable to establish connection with Cloudflare edge error="TLS handshake with edge error: EOF"`。

**判据**：看日志里的 `ip=` 字段。出现 `198.18.0.x` 就是被 Clash 的 **fake-ip** 接管了。
注意 DNS 劫持是全局的，**`dig @223.5.5.5` 也会返回 fake-ip**，本机拿不到真实边缘 IP。
同时若 `curl https://www.google.com` 是 200，说明**代理本身没坏**，
坏的只是 cloudflared 默认走的 QUIC/UDP 在 gvisor TUN 下握不上手。

**现行修法（已实施）**：让隧道边缘域名绕开代理直连。

1. `~/.cloudflared/config.yml` 加 `protocol: http2`（不走 QUIC）和 `edge-ip-version: "4"`
   （本机 IPv6 不通；**这个值必须是字符串，写成 `4` 会 `expected string found int` 启动失败崩溃循环**）。
2. Clash 侧两处（目录 `~/.local/share/io.github.clash-verge-rev.clash-verge-rev/`）：
   - 规则链 `profiles/rjovcsxPa1Pn.yaml` 的 `prepend:` 加 `DOMAIN-SUFFIX,argotunnel.com,DIRECT`
   - Merge profile `profiles/mxV9lDvqsuDj.yaml` 加 `dns.fake-ip-filter: ["+.argotunnel.com"]`

   **坑：不要去改 `dns_config.yaml`，那个文件是死的** —— Verge 的 DNS 覆写开关没开，
   运行时 DNS 段其实来自订阅。改 DNS 只能走 Merge profile。
   两处都是 Verge 的链式配置，**订阅更新不会冲掉**。
3. 热重载，不用重启 Clash GUI、不断 TUN（gdrive 挂载依赖它），返回 204 即成功：

   ```bash
   curl -X PUT --unix-socket /tmp/verge/verge-mihomo.sock \
        -d '{"path":"<clash-verge.yaml 绝对路径>","force":false}' \
        http://localhost/configs
   ```

**验证**：`getent hosts region1.v2.argotunnel.com` 应返回真实 `198.41.x` 而非 `198.18.x`；
`curl --unix-socket /tmp/verge/verge-mihomo.sock http://localhost/rules` 能看到规则且 hitCount 在涨。

**收益**：直连后边缘从经代理的 nrt（东京）变为 lax（洛杉矶），pms 首页 **5.69s → 1.28s**。

## 9. OCR 临时借用 .27 的 V100（V100 返修期间）

**背景**：.12 的 V100 返修，OCR 只剩 3070Ti 8G，而 PaddleOCR-VL 峰值需 10G，大文件必 OOM。
`.27`（172.1.14.27）是对标 OPMS 客户硬件的测试机，两张 V100 16G 一直空着，临时借来顶班。

**做法：不改任何调用方配置**。`.12` 本机的 `paddle-ocr.service` 停掉并 `disable`，
8118 端口换成一个 **TCP 转发**（`ocr-proxy.socket` + `ocr-proxy.service`，
用 systemd 自带的 `systemd-socket-proxyd`）指向 `172.1.14.27:8118`。

> 为什么用裸 TCP 转发而不是 nginx 反代：**纯透传不解析 HTTP，没有 body 大小限制、没有超时截断**，
> 大 PDF 上传和几十秒的 OCR 长响应都不受影响。
> 监听 `0.0.0.0` 是为了同时覆盖宿主的 `127.0.0.1:8118` 和容器经 `host.docker.internal`(172.17.0.1) 的调用。

于是这些调用方**全部零改动**：PMS 投标审查、doc-intake(9080)、officer-agent、bid-review(9010)，
以及 ocr-multi(8119)——它本来就是反代 8118 拿 VL 的，所以自动跟着走。

**`.27` 侧**：`/etc/systemd/system/paddle-ocr.service`，跑的是从 .12 拷过去的同一份
`ocr_server.py` + `ocr_export.py`（在 `/home/z/paddle-ocr/svc/`），
用 `/home/z/paddle-ocr/.venv_paddleocr`（paddleocr 3.7.0 / fastapi 0.138.1，与 .12 完全同版本）。
已 `enable`，.27 重启会自恢复。只用了 GPU0，**GPU1 还空着**，将来要提吞吐可再起一个实例。
注意 `CCGP_THROTTLE=0` —— .27 没有 ccgp 服务，不关掉的话每次干活都会去 `systemctl` 报错。

**顺带的好处**：3070Ti 空出来后，bge-m3 从 CPU 挪回了 GPU，**短查询 73ms → 20ms**。

**风险**：`.27` 关机或网络不通，`.12` 的 OCR 会直接连不上（以前至少还能本地跑）。

**收回（V100 修好装回来之后）**：一条命令，会自动按 UUID 锁卡、验证没有静默退回 CPU、并停掉 .27 的顶班服务。

```bash
sudo -v && bash ~/cgb/ocr_revert.sh
```
