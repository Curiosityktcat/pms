# 资料智能归档（doc-intake）

- 容器：`doc-intake`，端口 **9080**，代码 `~/platform/services/doc-intake/`
- 数据卷：`platform_intake-data` → 容器内 `/data`（宿主 `/var/lib/docker/volumes/platform_intake-data/_data`）
- 入口三处：PMS 工具栏「资料智能归档」（同源反代，内外网都能用）、内网总台卡片、直连 `http://172.1.14.12:9080`

## 1. 主链路

```
拖进文件
  → 取文字（数字件直取 / 扫描件 OCR）
  → LLM 判类 + 抽字段（本地 Qwen，走 llm-gateway）
  → 按类型归档到目录
  → 若认出采购项目编号 → 移交 agent 研判 → 挂进经办人待确认清单
```

## 2. 取文字策略（`extract.py`）

用户定的口径：**识别要准，默认就跑 Paddle-VL，只有明确要快才用快引擎。**

| `engine` | 行为 |
|---|---|
| `auto`（默认） | 数字件直取（文字层可信才算数）→ 扫描件走 **PaddleOCR-VL**；VL 失败重试一次，仍失败才降级 RapidOCR 并在 `source` 标注「VL降级」 |
| `vl` | 不信文字层，一律走 VL（文字层乱码、混排时用） |
| `fast` | 走传统 PP-OCR（`8118 /ocr_classic`），失败退 RapidOCR |

传参：`-F engine=vl`。默认值由 env `INTAKE_ENGINE` 控制。

### 「是不是扫描件」怎么判（这条最影响准确率）

**坑**：政采平台下载的扫描件，页面里**嵌了约 90 字符的真文字水印**（"四川政府采购一体化平台 N511… 第1包 时间"）。老逻辑「超过 40 字符就当数字件」被骗过去，**直取只拿到水印、正文全丢**，喂给分类模型等于空的。

现在 `_pdf_is_scanned()` 按两条判：

- **累计图像覆盖率 ≥ 25%**（扫描图常只占页面上半，所以不是整页阈值）**且页文字 < 400 字符** → 扫描页
- 或页文字 < 100 字符 → 扫描页
- 过半页面像扫描件 → 整份走 OCR

另有文字层可读率门槛（可读字符占比 ≥ 0.75、长度 ≥ 120）。

env 可调：`INTAKE_SCAN_IMG_COVER` / `INTAKE_SCAN_TEXT_MAX` / `INTAKE_MIN_TEXT_CHARS` / `INTAKE_MIN_TEXT_QUALITY` / `INTAKE_OCR_PAGES`（默认只 OCR 前 2 页，分类够用）。

**实测对比**（同一份扫描件，第 20-21 页竖排+盖章）：修前"直取 198 字符全是水印" → 修后 **VL 1330 字符**，判类正确；同页 `engine=fast` 17s 但识别成"订型具业型电室"这种乱码。

## 3. 判类与归档

- 判类模型：**本地 Qwen3.6-27B**（env `INTAKE_PROVIDER`，经 llm-gateway；带 `enable_thinking:false`），DeepSeek 作 fallback
- 17 种档案类型，映射表 `CATMAP`（`app.py`）
- 项目编号正则：`SJZB-\d{4}-\d{6}`、`SCJD…`、`SCATZY-?\d+`、`NJYGCG\d+`、`NJYYJX[-\w]*`、`N511\d{6,}`、`N\d{9,}`

归档两棵树，由「能不能认出项目编号」决定落哪棵：

```
/data
├── 项目/<项目编号>/<前期|中期|后期|其他>/<环节>/<id前8位>_<原文件名>
└── 分类库/<前期|中期|后期|其他>/<环节>/…
```

## 4. 接口

| 接口 | 用途 |
|---|---|
| `POST /upload` | 主链路：上传 → 识别 → 判类 → 归档（表单 `file`、可选 `engine`/`uploaded_by`/`project_no`） |
| `POST /extract` | 只取文本，不判类不落库（给 agent 读文档用） |
| `POST /classify` | 只判类 |
| `GET /docs` / `GET /doc/<id>` / `GET /file/<id>` | 归档记录列表 / 详情 / 下载原件 |
| `POST /doc/<id>/agent` | **agent 回写研判/确认状态** |
| `GET /stats` | 统计 |

`docs` 表字段：`id, ts, filename, doc_type, confidence, project_no, purchaser, counterparty, doc_date, amount, summary, target_path, stored_path, ocr_chars, ocr_text, uploaded_by, agent_status, agent_verdict`。

## 5. 两段式 agent 链路

用户设计的两棒交接：

```
① 分类 agent（doc-intake 9080）
     识别归档 → 落到「项目/<编号>/…」= 认出采购项目
     → 后台线程移交（不拖慢上传响应）
②  牛马 agent（pms-agent 3070）POST /api/doc_intake
     查 PMS 项目（注意字段是 number 不是 project_number，两个都要兜底）
     + 调 llm-gateway 研判 {related, stage, doc_kind, summary, reason, risk, suggestion}
     → 挂进经办人待确认清单
③ 经办人在牛马页面右栏「📂 资料确认」点【确认收录 / 否决】
     → 状态回写 doc-intake（POST /doc/<id>/agent）
```

- 牛马侧接口：`POST /api/doc_intake`、`GET /api/docs`、`POST /api/docs/act`
- 队列持久化：`/data/intake_docs.json`（`pms-agent-data` 卷）
- 开关：`AGENT_HOOK=0` 停止移交；`AGENT_HOOK_URL` 改目标
- **只有认出项目编号的才移交**，分类库里的普通资料不打扰经办人

**实测闭环**：造一份中标通知书（真实编号 `NJYYJX-ZZ-2607009`）→ 判类「中标成交通知书」+ 编号/供应商/金额全对 → 归档 `项目/NJYYJX-ZZ-2607009/后期/中标成交通知书` → 牛马匹配到项目、判 `related=true` / 环节=中标成交 / risk=yellow，**并额外发现「立项方式是院内竞选、通知书写竞争性磋商」的不一致** → 点确认 → doc-intake 状态变「已确认」。

## 6. 改这个服务的注意事项

- 改代码后必须 `cd ~/platform && docker compose build doc-intake && docker compose up -d doc-intake`（**只 restart 不换镜像层**）
- 归档树里的文件路径记在 `intake.db` 的 `target_path`/`stored_path`，**不要在文件系统里直接移动或改名**，否则记录对不上
- 老库加字段用 `ALTER TABLE … ADD COLUMN` 包在 try 里（`app.py` 已有这个平滑升级写法）
