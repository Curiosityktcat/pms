## v0.18.5 · 2026-08-14 · `改进` OCR 临时借用 .27 的双 V100，bge-m3 回到 GPU

V100 返修期间 OCR 只剩 3070Ti 8G，而 PaddleOCR-VL 峰值需 10G，大文件必 OOM。
把 OCR 整个转到 `.27`（两张 V100 16G，一直空着）顶班。

**关键点：所有调用方零改动。** .12 的 8118 停掉本机服务，换成 TCP 转发指向 `172.1.14.27:8118`，
所以 PMS 投标审查、doc-intake、officer-agent、bid-review、ocr-multi 都不用改配置。
用裸 TCP 透传而不是 nginx 反代，是因为不解析 HTTP 就没有 body 大小限制和超时截断，
大 PDF 上传和几十秒的长响应都不受影响。

**顺带**：3070Ti 空出来后 bge-m3 从 CPU 挪回 GPU，短查询 **73ms → 20ms**。

**实测**：中文合同测试图经 .12:8118 转发识别 4/4 全对；
doc-intake 整链路（上传→OCR→本地判类→归档）通，`source: paddleocr-vl`，
项目编号/采购人/供应商/金额/日期全部抽对（测试记录已清理）。

**风险**：`.27` 关机或网络不通，`.12` 的 OCR 会直接连不上。

**收回**：`sudo -v && bash ~/cgb/ocr_revert.sh`（自动按 UUID 锁卡、验证没静默退回 CPU、停掉 .27 顶班服务）。
详见《运维手册》第 9 节。

**要不要重启**：paddle-ocr / bge-m3 已处理；PMS 本身没动，不用重启。

## v0.18.4 · 2026-08-14 · `修复` 重启后 bge-m3 崩溃循环、OPMS 不自启、公网 Error 1033

一次机器重启暴露出三个问题，都不在 PMS 代码里，但都会让人以为「PMS 坏了」。

**1. bge-m3 崩溃循环（影响最大，最难发现）**

`systemctl is-active bge-m3` 报 **active**，实际每 25 秒挂一次重起一次，restart counter 已到 11。
根因是 8-13 换卡时留下的临时配置把它放在 3070Ti 上，而 PaddleOCR-VL 常驻已占 7.2G/8G，
**只剩 243MiB**，bge 要 577MiB 就 `cudaMalloc failed: out of memory`。
bge-m3 是全局嵌入模型，PMS 投标审查 / cga-rag / okf-kb RAG 全靠它。

> **教训：`systemctl is-active` 报 active 不等于服务活着。**
> `Restart=on-failure` 的崩溃循环也是 active。判据用 `systemctl show <svc> -p NRestarts --value`。

修法：加 drop-in `/etc/systemd/system/bge-m3.service.d/zz-nogpu.conf` 改走 CPU
（`--device none -ngl 0 -t 8`，短查询 73ms 够用）。文件名**故意 zz 开头**，
字典序要压过已有的 `cuda.conf` 才能覆盖 `ExecStart`。
V100 装回后 `rm` 这个文件 + `daemon-reload` + `restart` 即恢复 CUDA。

**2. OPMS(9100) 不开机自启**

原来是手工 `venv/bin/python backend/app.py` 起的，一重启就没了。
已收编为 `opms.service`，见 opms 仓库 `deploy/README-systemd.md`。

**3. 公网全站 Error 1033**

Clash TUN 的 fake-ip 劫持了 cloudflared 到 Cloudflare 边缘的连接。
完整判据与修法见《运维手册》第 8 节。
顺带把隧道改成直连绕开代理，**pms 首页 5.69s → 1.28s**。

**另外两件不是 bug 的事**

- **重启后所有人被登出**是预期行为：30 分钟滑动空闲过期，机器关着没有请求刷新，
  回来就被弹到 `/login?expired=1`。
- **V100 彻底不被识别，已送返修**。互换法证明槽是好的（3070Ti 在两个槽都点亮，
  V100 在两个槽都点不亮）。期间 OCR 挤在 3070Ti 8G 上，
  **PaddleOCR-VL 峰值需 10G，大文件会 OOM**，备用算力是 `.27` 的两张 V100。

**要不要重启**：bge-m3、cloudflared-pms 已重启；PMS 本身没动，不用重启。

## v0.18.2 · 2026-08-11 · `修复` 公网传大文件 524 失败（OSS 中转直传）

**改了什么**
- 新增 `backend/services/upload_relay.py`：**OSS 中转直传**。浏览器把文件直传到 OSS
  的本人专属暂存区（绕开 Cloudflare），业务接口凭 `oss_key` 把它拉回**原来的本地路径**，
  落盘之后一切照旧——下载、预览、删除、rd-web 推送等读文件的代码一行没动。
- `backend/routes/storage_api.py`：新增 `staging` 模块的签名（`upload_relay.staging_rel`），
  并挂上暂存区兜底清理（签名接口顺带跑，最多一小时一次，收拾「传了但没点保存」的漏网对象）。
- **13 个上传口接入中转兜底**（`f = request.files.get("file") or upload_relay.staged_file()`）：
  合同正文 / 合同附件 / 公告附件 / 投标文件审核 / 采购结果（中标通知书 + 报价附件）/
  采购文件附件 / 询价（2 处）/ 询价评审 / 代理协议 / 科室公告 / 采购需求（2 处）/ 项目分发。
  **纯兜底**：前端不发 `oss_key` 时行为与改造前一字不差。
- 新增 `frontend/src/services/upload.ts`（`smartUpload` / `smartUploadAbs`）：
  先问 `/api/storage/status`，公网且文件 ≥4MB 才走中转，**局域网一律走老路**
  （内网直连 2ms、千兆、不计流量费，绕成都反而慢）；**直传失败自动回落**服务器中转，
  宁可慢也不能传不上去。
- 前端接入：`services/contract.ts`（正文+附件）、`pages/AnnouncementPage`、
  `pages/CorrectionAnnouncementPage`、`pages/SurveySingleSourcePage`、
  `pages/ProcurementResultPage`（报价附件+中标通知书）、`components/DocAttachmentsModal`、
  `pages/BidReviewPage`（投标文件，动辄上百 MB，收益最大）。顺带清掉 6 处不再使用的 axios 导入。

**为什么**
用户公网传 40MB 失败。**实测定位（同一台机器同一时刻）**：
- 40MB 走 `pms.curiosityktcat.cn` → **131 秒时 HTTP 524**，即 Cloudflare 免费版
  **100 秒源站超时**。同链路 5MB 也要 **86.8 秒**（0.06 MB/s）。
- 同样 40MB **直传 OSS（成都）→ 4.3 秒**（9.35 MB/s）。差 30 倍。
- 内网同一文件 0.5 秒。

所以**公网上传的瓶颈从来不是 100MB 体积上限，而是慢到触发 100 秒超时**——40MB 远没到
100MB 就已经失败了。v0.18.1 修的是内网的前端 15 秒超时，与这条是两回事。

**为什么是「中转」而不是把这些模块整体搬到 OSS**
合同、采购结果等模块的下载、预览、删除、rd-web 推送等六七处代码都直接按本地路径读文件；
把存储整体换掉要连带改全部读点，风险大。中转只改「收文件」这一步，落盘位置不变。
代价是多一次 OSS 下行流量（0.25~0.5 元/GB），按当前用量每月几毛钱。

**安全**
暂存对象的键会回传给服务端，所以键里带一段用 `SECRET_KEY` 派生的**本人专属目录名**
（`uploads/_staging/<hmac16>/…`），服务端只认属于当前登录人的键——**实测拿别人的键认领会被拒**。
取走后立即删除暂存对象；漏网的由兜底清理按 24 小时收走。

**怎么验证**（`~/pms/tests/smoke_relay_upload.py`、`smoke_relay_announcement.py`）
- 合同附件 40MB 走公网全链路 **12 项全过**：签名 → 直传 OSS 2.7s → 业务接口取回 1.4s →
  大小/文件名一致 → **文件真落到本地 `uploads/contracts/19/attachments/`** → 下载字节一致 →
  暂存对象已清 → **他人暂存键被拒** → 局域网普通 multipart 仍 200 → 测试附件清理干净。
- 公告附件 40MB 走公网 **8 项全过**（三个页面共用这个口）。
- v0.18.1 的内网回归 `smoke_transfer.py` **13 项全过**，无回踩。
- `tsc -b` 类型检查通过；构建产物确认含中转逻辑。

**要不要重启**
- 后端改了 `storage_api.py` / `upload_relay.py` / 13 个 routes → **要** `sudo systemctl restart pms.service`（已执行）。
- 前端已 `npm run build`（已执行）。浏览器需**强刷一次**（Ctrl+F5）。

**还没接的**（仍走老路，公网传大文件仍会 524）
`services/inquiry.ts`、`agencyAgreement.ts`、`deptAnnouncement.ts`、`procurementDemand.ts`、
`projectDistribution.ts` 这几个前端调用点还没换成 `smartUpload`（**后端已经支持**，只差前端一行）。
另外「我的文件库」（filebox）不在其中：它的文件要落在 `~/files` 供 SFTP 式浏览，
且主要是内网使用场景。

## v0.18.1 · 2026-08-07 · `修复` 内网大文件传不上去（前端 15 秒超时）

**改了什么**
- `frontend/src/services/api.ts`：axios 实例的 `timeout: 15000` 原来对**所有**请求生效，
  文件上传也吃这个超时。改为加请求拦截器——**请求体是 FormData、或 `responseType` 是
  blob/arraybuffer 时自动把 timeout 置 0**（免超时）；调用方显式写了 timeout 的
  （OCR 300s、rd-web 60s、API 测试 70s）保持原值不动。
- `frontend/src/services/filebox.ts`：
  - 上传**按 200MB 分批**（原来所有文件塞进一个 POST）。传到一半断掉只损失当前这批，
    前面的已落盘；进度条跨批累计；失败时告诉用户前面几个已成功、只需重传剩下的。
  - 新增 `downloadFileNative` / `downloadFolderNative`：**超过 150MB 的文件与所有文件夹 zip
    改走浏览器原生下载**，不再走 blob。
- `frontend/src/pages/FileBoxPage.tsx`：下载按钮按文件体积自动选择 blob（带进度条）或原生下载。
- `backend/routes/filebox_api.py`：上传失败的提示语原来把内网问题也甩给 Cloudflare 100MB 上限，
  误导排查方向。改为按现象分三种情况说明，主因写「上传中途被中断」。
- `backend/app.py`：`/doc-intake-svc/` 与 `/officer-agent/` 两个同源反代原来用 `request.get_data()`
  **把整个上传体读进 PMS 进程内存**（291MB 的件要占两三份），改为流式转发（`request.stream` +
  `iter_content`）。**坑**：直接把 stream 交给 requests，它算不出长度会自己加
  `Transfer-Encoding: chunked`，与转发的 `Content-Length` 并存 → 对端 gunicorn 判非法头返回
  400 Invalid HTTP Header；解法是用 `_StreamBody` 包一层给出 `.len`，让 requests 只发
  Content-Length（这个坑第一版就踩了，测出来才改对）。

**为什么**
黄新博在内网传 291MB 到「我的文件库」失败。服务端日志是
`[filebox] upload 未收到文件 content_length=305233184 form_keys=[] files_keys=[]`。
**关键线索：连 `path` 这个几字节的小字段都没解析出来**——前端 FormData 是先 append `path`
再 append 文件的，如果只是文件传一半，`path` 应该在。真因是 Werkzeug 解析 multipart 时
中途遇到 EOF 会抛 ValueError，被 `FormDataParser` 静默吞掉（默认 silent），**连已经解析好的
字段一起丢弃**，于是 form/files 双空且不报错。而 EOF 的来源就是浏览器在第 15 秒 abort 了请求：
291MB 要在 15s 内传完需要持续 160Mbps 以上，Wi-Fi 或百兆口根本到不了。
日志里的 `content_length` 只是客户端**声明**的 Content-Length，不代表真收全了——这一点当时的
提示语理解错了，才会去怀疑 Cloudflare（内网直连根本不经 Cloudflare）。

**怎么验证**（回归脚本 `~/pms/tests/smoke_transfer.py`，21 项全过）
- 291MB 真实 HTTP 上传 → 200，2.3s，落盘字节数一致（305,135,616 B）。
- 模拟浏览器中途 abort（声明 200MB 只发 1MB 就断）→ 400，提示为
  「未收到文件（客户端声明 200 MB）（上传中途被中断：浏览器超时、切走页面或网络掉线…）」。
- 291MB 下载 → 200、字节数一致、带 `Content-Disposition: attachment`（原生下载才会落盘）。
- 文件夹打包 zip 291MB → 200；`/tmp` 无残留（`after_this_request` 清理正常）。
- 反代流式实测：200MB body 过 `/doc-intake-svc/` → **PMS 常驻内存 122MB 全程不涨**（改前会整份进内存）。
- doc-intake 反代 GET/POST、officer-agent 反代 GET/POST 均通。
- `tsc -b` 类型检查通过；构建产物里确认含拦截器、分批常量、150MB 原生下载阈值。

**要不要重启**
- 后端改了 `app.py` / `filebox_api.py` → **要** `sudo systemctl restart pms.service`（已执行）。
- 前端改动已 `npm run build`（已执行）。用户浏览器需**强刷一次**（Ctrl+F5）才会拿到新 bundle。

**顺带记录**（排查时确认的现状）
- PMS 现在跑的是 **gunicorn**（1 worker / gthread 24 线程 / `--timeout 600`），不再是 Flask 开发服务器。
- 文件库上传遇到同名文件是**直接覆盖**（SFTP 语义），本次未改，注意别用同名文件覆盖旧件。

## v0.18.0 · 2026-08-06 · `新增` 投标文件电子痕迹取证（bid-forensics 9090）

**改了什么**
- 新增平台业务服务 `bid-forensics`（端口 9090，`~/platform/services/bid-forensics/`）：
  比对多家投标人标书的软件序列号、文档元数据与硬件标识，判「四个同一」串通投标线索。
- 能挖到的关键证据：**WPS 设备硬件标识 hdid**（写在 `docProps/custom.xml` 的 base64
  `KSOTemplateDocerSaveRecord` 里，跨文档跨账号稳定，是唯一能从文件内部穿透到硬件层的通道）、
  WPS 内容校验值 ICV、末次保存者、Word 文档 GUID、rsid 编辑会话重叠、**内嵌公章/证照图片指纹**、

**为什么**

任意两家只要都用了 python-docx 就"完全一致"。所以服务内置**基线校正**：这类值一律剔除并写明原因，
只让真正有区分度的特征进比对。

**怎么验证**

## v0.17.1 · 2026-08-04 · 换 gunicorn ＋ 干掉 /api/projects 的 N+1（145ms → 28ms）

### 改进 · Flask 开发服务器 → gunicorn

`pms.service` 改用 gunicorn，**单 worker + gthread 24 线程**，超时 600s。
**为什么不是多进程**：PMS 有大量进程内状态——rd-web 常驻会话池（活着的 Chrome）、
抓取/推送的运行标志 `_state`、消息去重表。多 worker 会各记各的，表现为
「点了抓取查不到状态」「会话池反复重登被限流」「推送锁失效」。
gthread 保住这些状态，同时拿到生产级 HTTP 服务（超时、优雅重启、连接管理、访问日志）。
回滚：`sudo bash ~/apply_gunicorn.sh --rollback`（原 unit 备份在 `pms.service.bak.devserver`）。

### 改进 · SQLite（WAL 其实早就开着，增量是另外三点）

盘点后发现 `journal_mode=wal` 当初为投标审查后台线程就开了，所以「开 WAL」没有增量。真正补上的是：

- **`synchronous` FULL → NORMAL**（连接级 PRAGMA，每条新连接都设）：提交不再每次 fsync。
  **代价：突然断电可能丢最后几个事务**（库本身不会损坏）。要最高持久性就改回 FULL。
- **`busy_timeout` 5s → 15s**：写高峰先等锁，而不是直接抛 `database is locked` 报 500。
- **WAL 定期检查点**（默认每 10 分钟 `wal_checkpoint(TRUNCATE)`）：WAL 已涨到 9.9MB 没回收；
  它越大，**别的服务读 pms.db 快照看到的数据越旧**（llm-gateway 踩过，当时得手动 checkpoint）。
  实测检查点线程生效：WAL 9.5MB → 4KB。

### 修复 · `/api/projects` 的性能真凶是代理机构 N+1

**先入为主猜错了一次**：以为慢在 `stage_map`（给 207 个项目算流程阶段），先优化了它——
ORM 实体查询改列查询、状态过滤下推 SQL，确实快 2.3 倍（30ms→13ms，371 项结果逐一比对全等），
但接口总耗时几乎没动。**上 cProfile 才看到真凶**：`get_agency_detail` 被调用 1035 次
（5 次请求 × 207 个项目）占 68% 耗时——每个项目单独查一次代理机构，而代理机构总共十几家。

改法：`_agency_map()` 循环外一次性读成字典，循环内查字典（单个用法的 `get_agency_detail` 保留不动）。
**207 个项目的代理字段与旧实现逐项比对完全一致。**

### 实测

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| `/api/projects` 单次 | 145ms | **28ms**（5.2×） |
| 24 并发总耗时 | 11.36s | **3.65s**（3.1×） |
| 局域网首页 | — | 1.7ms |

回归 7 项全过：业务接口、24 并发全 200、牛马反代、rd-web 会话池状态、对象存储配置、WAL、内网选路。

## v0.10.0 · 2026-07-28 · rd-web 常驻登录 + 调研公告/单一来源公示 + 牛马会办公

### 新增 · rd-web 常驻登录会话池（不再频繁登录被限流）

痛点：每提交一次就重新登录一次，账号很快被站点判「登录太频繁」，一限流所有自动化全停。

**为什么不能简单地把会话存下来**——这是本项目踩过的坑，写在这里免得以后再踩回去：
人员选择组件 `choosePerson_new` 的 user_id/token **只在真实登录过程中注入内存**，
不落 cookies / localStorage / sessionStorage。带序列化的旧会话进来会跳过登录，
结果经办人弹框「我的」部门树永远为空 →「未找到经办人」。实测同一会话文件 30 分钟后即坏。

所以做法是 **保持浏览器活着，而不是把会话存下来**：

- 新建 `services/rdweb_session.py`：每个账号常驻一个 Playwright browser + context + page，
  登录一次后一直留着，后续任务复用同一个 page，靠 SPA 内部点击导航（不做整页 goto，
  否则内存里的 token 会丢）
- **两个账号 = 两个互不相干的上下文，可以同时在线**（黄新博与郑跃俊各自保持登录）
- 生命周期：首次真实登录 → 之后先探活，活着就直接复用 → 超过 6 小时或探活失败才重新登录
  → 空闲 2 小时自动关掉释放内存（后台回收线程，随 PMS 启动）
- 出错时丢弃该会话，下次重新登录，避免一个坏会话让后续每次都失败
- 新增 `GET /api/rdweb/contract/sessions` 看谁在线（手机号打码，不含凭据）、
  `POST /api/rdweb/contract/sessions/reset` 强制重登
- `contract_submit` 与 `procurement_approval_submit` 都已接入

**实测**：郑跃俊账号第一次 36.9 秒（真实登录），第二次 **4.9 秒直接复用、登录次数仍为 1**。

评审委员会已完成评审，结果无法再改，采购人若不认可，走的不该是「打回去改」。所以单独做了一条路径：

`待确认` --采购人不认可，写明原由--> `不确认` --代理机构复核，给出处置--> `待确认`（重新推送）

- `POST /api/procurement-results/<id>/not-confirm`，必须写明不认可的原由
- `POST /api/procurement-results/<id>/recheck`，处置四选一：**维持原结果 / 废标 / 部分废标 / 顺延候选人**，须填复核说明；选「部分废标」或「顺延候选人」时先改分包内容再提交复核
- 前端在「9. 采购结果确认」页把「驳回」和「不确认此结果」做成两个按钮，各自带说明，避免用错

### 新增 · 归档件《审批过程记录表》

`services/approval_record_word.py` + `GET /api/archive/<pid>/approval-record`。把该项目所有往返按时间排成一张表（时间/环节/轮次/动作/操作人/原因），归档文件夹里新增「审批过程记录」一栏，文件名上直接标注共几次往返、其中驳回几次。无往返的项目也出表，注明「各环节均一次通过」。

### 改进 · 待办自动派单（原来做得不好，要自己新建业务）

`services/system_todos.py` 重写。原来只有 7 个事件、且一个环节固定归一方；现在 **24 个事件**，归属**随单据状态在代理机构与经办人之间自动传递**。

以采购公告为例：无公告/草稿 → 代理「待编制」；已提交 → 经办人「待确认」；被驳回 → 代理「待修改后重新提交」；已发布 → 本环节待办自动消失，下一环节（是否可开标）落到代理头上。

补齐的方向：采购公告待确认、更正公告待确认与待修改、开标授权函、流标待确认、8.5 评审资料上传/确认/补件、采购结果编制/确认/复核、各节点被驳回后的回流，以及**院内询价、议价、紧急采购**整条轨道（原来完全没有派单）。被驳回类待办优先级自动提到「紧急」——这类是卡住流程的返工。

### 改进 · 开标管理：筛选、搜索、日历视图

- 新增**经办人**、**代理公司**两个下拉筛选，以及关键字搜索（项目名称/编号/经办人/代理）
- 右上角**列表 / 日历**一键切换，选择记在浏览器本地
- 列表模式：按开标时间**升序**排列，越早开标的排在越前面
- 日历模式：按开标日期分成多个**大框**，框头显示星期与日期（今天会标出来）、右上角显示当日项目数，框内是该日的项目卡片——一眼能分清哪天开哪几个

### 改进 · 合并操作步骤（原来一件事拆成三步做）

6.1 采购公告、6.3 更正公告原先必须「新建 → 保存草稿 → 回来传附件 → 回列表点提交」四步。现在新建时就能选附件（先暂存，保存时自动上传），弹窗底部直接给「**保存并提交确认**」，一次点完。9 采购结果、10 合同原本已有「保存并提交」，本轮统一了交互。

### 改进 · 待确认页签移到最左并默认选中

## v0.4.0 · 2026-07-26 · OCR 提速三件事

### 改进 · ccgp 动态让路（4.7 倍）

发现 VL 推理慢的真因不是 GPU，是 `ccgp@ocr` 的 12 个 CPU worker 搅乱内存带宽（GPU 利用率全程只有 0~20%）。

- 新增 `~/cgb/ccgp_throttle.sh` + sudoers 白名单
- 8118/8119 在**推理期间**把 ccgp 限到 `CPUQuota=300%`，干完立刻解除，空闲时 ccgp 照常满速
- **实测：3 页 layout 176s → 37s**

走过的弯路（别再试）：`CPUWeight` 无效；**`AllowedCPUs` 限核帮倒忙**（paddle 110 个线程挤 8 核更慢）。

### 改进 · 按需只跑一趟

`vl_all` 加 `want=html,word,pdf` 参数。只要 HTML+Word 就只跑 layout 趟（3 页 38s），只要双层PDF 就只跑 spotting 趟（74s），单样时直接返回文件不套 zip。

### 改进 · 单卡并发

- 端点从 `async def` 改 `def`（丢线程池）→ **推理期间 `/health` 从整个堵死变成 13ms 返回**
- 差异化闸门：**layout 可并发 2 路**（21s→12s，结果与串行逐字一致）；**spotting 必须独占**（并发必 OOM）

### 记录 · V100 卡的体检结论

怀疑过卡有问题，实测：fp16 算力 **87.6 TFLOPS**（对照机 89.8，97.5%），零 replay、零 AER 错误、不降频。**卡是好的**；有问题的是链路（PCIe `x2` 而非 x16，带宽只有对照机 1/10），但对 OCR 只值约 2%。
