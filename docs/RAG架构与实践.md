# 从"检索一次就回答"到"会反思的检索"：我们如何把 Agentic RAG 落进采购评审系统

> 一篇写给非纯技术读者也能看懂的实战笔记：借鉴 Google 的 Agentic RAG，
> 我们用极小的代价，把一套采购/投标评审系统的 AI 审查能力做了一次升级。

---

## 一、先把 RAG 说人话

RAG（Retrieval-Augmented Generation，检索增强生成）这个词听着唬人，其实就一句话：

> **先去资料里"查"，再让大模型据查到的内容来"答"。**

为什么需要它？因为大模型有两个天生的毛病：一是**会编**（训练数据里没有的、或记混的，它会一本正经地胡说）；二是**不知道你内部的资料**（你单位的招标文件、内控制度，它从没见过）。RAG 的办法就是：回答前，先把相关资料检索出来塞给模型，让它"看着材料说话"，既减少胡编，又能用上你的私有知识。

一个最朴素的 RAG 长这样：

```
用户提问 → 去知识库检索相关片段 → 把片段 + 问题一起给大模型 → 输出答案
```

这套"检索一次、直接回答"的流程，业界叫 **Naive RAG（朴素 RAG）**。它能用，但有个致命短板——**它不会反思自己"查得够不够"**。

---

## 二、朴素 RAG 的天花板：它不知道自己漏了什么

举个真实场景的例子。问："X 项目用的服务器是什么配置？"

- 知识库里检索到了"X 项目"的文档，里面只写了一个服务器**型号编号**；
- 真正的**配置参数**在另一个设备库里。

朴素 RAG 检索一次，拿到第一份文档就开始作答——它**意识不到自己还缺一块**，于是要么答得残缺，要么干脆编一个配置出来。

这类"答案散落在多处、需要多步拼接"的问题，叫**多跳查询（multi-hop）**。朴素 RAG 在这里普遍翻车。

---

## 三、Google 的解法：让检索变成一个"会反思的智能体流程"

Google 在 Gemini Enterprise 的一篇文章里给出了 **Agentic RAG（智能体化 RAG）** 的架构，核心思路是：**把"检索"从一次性动作，升级成由多个专职角色协作、能反复补查的闭环流程。**

它拆出了五个专职角色：

| 角色 | 职责（说人话） |
|---|---|
| **Orchestrator（编排器）** | 总调度，判断问题复杂不复杂，派活 |
| **Planner（规划器）** | 规划"要回答这个问题，得按什么路径、从哪些库取哪些信息" |
| **Query Rewriter（查询改写）** | 把一个问题拆成多个更精准的检索查询 |
| **Search Fanout（检索分发）** | 把这些查询并行撒到不同数据源 |
| **Sufficient Context（充分性检查）** | **质检员——判断"查到的够不够回答"** |

其中**最关键的创新，是那个"充分性检查"角色**。它在模型给出最终答案前，先审三件事：检索到的片段相不相关、当前草稿有没有足够依据、**还缺什么**——而且给的是**具体反馈**，比如："你找到了用药和饮食信息，但漏了过敏史。"

一旦判定"不够"，它不让模型硬答，而是**回头触发再检索**。整个系统于是变成一个闭环：

```
检索 → 充分性检查（缺什么？）→ 针对缺口再检索 → 直到够了 → 综合作答
```

Google 给的数据：相比标准 RAG，在事实性数据集上准确率最多提升 **34%**，而且这种多轮迭代几乎不增加延迟。

**一句话总结它的灵魂**：不在于"用了几个智能体"，而在于**系统学会了"意识到自己还缺什么"并主动去补**，而不是查到什么就答什么。

## 四、回到我们的系统：差距在哪，又该补哪

我们这套采购/投标管理系统（PMS）里，有一个很重的 AI 功能——**投标文件智能审查**：把招标文件里的资格条件、实质性条款、商务要求、评分项一条条抽出来，再拿去逐条比对每一份投标文件，给出"满足 / 不满足 / 需核验 / 未找到"的初判。

对照 Google 的架构，我们盘了一下家底，发现一个朴素但诚实的现状：

- 我们其实**已经做了"任务分解"**——把抽取拆成 5 次专职的模型调用（概要、资格、实质性、商务、评分项各管一摊），这和 Google"专职智能体"是同一种思想；
- 但我们是**一条静态流水线**：走完就交卷，**缺了那个会反思的闭环**。一旦某个条款在投标文件里没被找到，系统直接记"未找到"，**它意识不到"也许是自己漏看了"**。

而在评标场景里，**漏判一条实质性条款是要出事的**。这正是 Google 那套架构最该补给我们的地方——**不是照搬五个智能体，而是补上那一个闭环。**

---

## 五、我们的落地：用最小代价补上"反思闭环"

### 1. 两轮闭环：让审查"回头再看一眼"

我们把投标审查的扫描逻辑改成了带反馈的闭环：

```
第 1 轮：全部条款 × 全部页，逐条初判（和以前一样）
   ↓
充分性检查：挑出仍然"未找到"的条款
   ↓
第 2 轮：只拿这批"未找到"的条款，带着"请更仔细地复查
        同义表述/不同章节/格式文件"的提示，再聚焦扫一遍
   ↓
仍找不到的 → 才是真·未找到，标记交人工复核
```

这里有个细节很关键：投标文件本来就被整份读过了，所以第二轮**不是"换页重查"，而是"缩小范围、聚焦重读"**。第一轮里每批要同时应付几十个条款，模型注意力被稀释，真实存在的响应可能被漏看；第二轮只盯着少数没找到的条款重读，注意力集中，能把被漏看的捞回来。

**成本是受控的**：第二轮只在"确实有未找到的条款"时才触发，而且只扫那几条，不是全量重来。轮数还可以一键关掉（一个配置开关，默认最多两轮）。

### 2. 混合检索：让"找资料"不再只会死抠关键词

抽取条款时，我们原来靠**关键词子串匹配**来挑相关页面——招标文件写"业绩"能匹配，写"类似项目经验"就漏了。

我们给它加了一层**语义召回**：用嵌入模型（Embedding）把每一页和"查询意图"都转成向量，按语义相似度把**关键词漏掉但意思相关**的页面补进来。最终是**关键词命中页 + 语义相似页 + 兜底页**的混合策略。

工程上特意做了减法：**单篇文档、几百页量级，在内存里算余弦相似度就够了，不需要任何向量数据库**。而且——**没配嵌入服务时，它自动退回原来的纯关键词行为，零风险**。

### 3. 本地化与降本：好钢用在刀刃上

我们手里有两块显卡：一块跑 OCR，一块（AMD 7900 XTX，24G）跑本地大模型 Qwen3.6。在线的 DeepSeek 强但按量收费，本地 Qwen3.6 免费但慢一些。

我们写了个对比小工具，拿同样的评审提示词让两个模型同台 PK。结论很实用：

- **本地 Qwen3.6 质量完全够用**（承诺制判定、法条引用都答到位），就是单次慢一些；
- 所以策略是**按场景分流**：投标审查这种后台批处理、不催延迟、量又大的活，交给**本地免费的 Qwen3.6**；AI 助手这种用户在前台等结果的，留给**快的 DeepSeek**。
- 嵌入模型也走本地（在那块 24G 卡上多起一个轻量服务，只占 ~1G 显存），**和在线服务彻底脱钩，不额外花钱**。

## 六、我们没做什么，以及为什么

做架构，"不做什么"往往比"做什么"更重要。我们刻意没有：

- **没上向量数据库**：单篇文档内存算相似度足矣，引入 faiss/chroma 是过度工程；
- **没搬五个智能体全套编排**：对我们当前规模太重，价值最低；
- **没把所有任务都推给在线大模型**：那是在持续烧钱。

我们只抓了**投入产出比最高的那一个点——反思闭环**，再配上混合检索和模型分流。这就是这篇 Google 文章给我们最实在的启发：**先想清楚你的瓶颈是什么，再决定借鉴架构里的哪一块，而不是看到漂亮的架构就全盘照抄。**

---

## 七、给同行的几条可复用经验

1. **先体检，再开方**：搞清楚自己到底是"朴素 RAG"还是"连检索都没有"，瓶颈在召回、在反思、还是在生成。
2. **闭环 > 堆智能体**：让系统"知道自己缺什么"，往往比增加角色数量更能提升可靠性。
3. **能内存算就别上数据库**：数据规模决定架构，不要被大词带跑。
4. **优雅降级是底线**：新能力（如语义检索）失效时要能自动退回旧行为，上线才敢灰度。
5. **本地与在线分流**：按"延迟敏感度 × 调用量 × 成本"给任务分配模型，既省钱又不牺牲体验。
