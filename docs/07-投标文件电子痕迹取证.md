# 投标文件电子痕迹取证（bid-forensics）

- 容器：`bid-forensics`，端口 **9090**，代码 `~/platform/services/bid-forensics/`
- 入口：内网总台卡片、直连 `http://172.1.14.12:9090/`、经网关 `http://172.1.14.12:8088/api/forensics/`
- **纯 CPU 解析，不调 LLM、不调 OCR、不碰数据库，无状态**，与 bid-review(9010) 相互独立

## 它和「投标文件审核」(9010) 的分工

| | bid-review 9010 | bid-forensics 9090 |
|---|---|---|
| 看什么 | 标书**正文内容**是否满足评审条款 | 标书**文件本身**的电子痕迹 |
| 手段 | OCR + LLM 逐条比对 | 解析文件容器与元数据 |
| 输入 | 单家投标人 + 评审要素 | **多家**投标人的文件 |
| 产出 | 符合/不符合 + 页码证据 | 「四个同一」串标线索 + 可疑度评分 |

两者互不依赖，可分别使用。

## 判什么——「四个同一」

监管审计判串通投标看四条：同一文档标识、同一硬件指纹、同一加密介质、同一网络轨迹。
只要任一项成立且投标人给不出合理解释，即可依《招标投标法实施条例》第四条认定相互串通。

**注意：这是比对性判据。** 只传一家的文件，服务返回「无法判定」，不出任何结论——这是设计如此，不是故障。

## 能从文件里挖到什么

**最有价值的一条：WPS 设备硬件标识 hdid**
WPS 会把本机硬件指纹写进 `docProps/custom.xml` 的 `KSOTemplateDocerSaveRecord`（base64 后是
`{"hdid":"..."}`）。它跨文档、跨账号稳定，是本服务唯一能从文件内部穿透到**硬件层**的通道。
两家投标人的 docx 出现同一 hdid ＝ 同一台机器制作标书，权重 100，单项即可推定。

其余：WPS 内容校验值 ICV、办公软件精确版本、末次保存者、创建者、Company、Word 文档 GUID、
rsid 编辑会话（含跨投标人重叠）、**内嵌图片指纹**（公章/营业执照/签名同图是强证据）、
PDF `/ID` 与 Producer、扫描件 EXIF 机身序列号与机型、JFIF 扫描分辨率。

支持 `.docx/.xlsx/.pptx`（含 WPS 产物）、`.doc/.xls`（OLE2 老格式）、`.pdf`。

## 文件里拿不到、必须外部调取的

MAC、上传/内网 IP、机器特征码、硬盘序列号、CPU ID、主板 UUID、CA 锁编号、计价软件锁号。
**这些不承载于投标文件内部**，只能向电子交易平台或 CA 机构调取。界面上每家投标人下有
「补录平台侧数据」折叠区，填进去就一起参与比对；没填的会在结果里列成「待补取证清单」。

## ★ 基线校正——这个服务最要紧的设计

很多"看着像证据"的值其实是工具固有的。最典型的：**python-docx 生成的 docx**，其
`dcterms:created` 恒为 `2013-12-23T23:15:00Z`、customXml `itemID` 恒为
`{EF278816-EC6F-A645-907D-7F25AECB1D4A}`、自带 9 个固定 rsid。任意两家只要都用了
python-docx，这些值就"完全一致"——直接拿去比对会得出"同一文档 UUID"的错误结论。

同类还有：WPS 写 zip 包的固定时间戳 `2012-07-02 09:52:14`、Word 的 `1980-01-01`、
以及 `Administrator`/`admin`/`user` 这类无区分度的默认用户名。

服务对每个提取到的值先过 `_is_baseline()`，命中的**不进比对**，转入 excluded 并写明剔除原因，
界面和 Word 报告里都能点开查看。**实测**：拿同一台机器另存的两份标书 → 460 分「高度可疑」；
拿另一家用 python-docx 独立编制的标书作对照 → **0 分「未见共同点」**，尽管它与前者共享
创建者、创建时间、itemID、9 个 rsid、模板全部五项固有值。

> 维护原则：新发现的通用值往 `forensics.py` 的 `GENERIC_NAMES` / `PYDOCX_*` / `ZIP_TS_CONST` 加。
> **宁可多剔除一个弱特征，也不要让一个通用值制造冤案。**

## 评分与等级

共享特征按权重累加，取两两配对最高分定级：

| 分数 | 等级 | 处置 |
|---|---|---|
| ≥100 | 高度可疑 | 建议依《条例》第四条要求相关投标人作出书面解释 |
| 60~99 | 重点核查 | 应调取平台侧数据进一步核实 |
| 25~59 | 需要留意 | 弱共同特征，结合其他线索判断 |
| 1~24 | 轻微雷同 | 仅软件环境等通用共同点，通常不具证明力 |
| 0 | 未见共同点 | — |

## 怎么用

1. 打开 `http://172.1.14.12:9090/`，填项目名称。
2. 每家投标人一个分组，填名称，把该家的标书文件拖进去（可多份、多格式）。
3. 有平台侧数据的展开「补录」填 IP/MAC/机器码/CA 锁。
4. 「开始取证比对」看结论；「导出 Word 报告」出正式件。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/healthz` | 健康检查 |
| GET | `/signals` | 信号定义表（供 agent 了解本服务能力） |
| POST | `/extract` | `file=` 单份 → 特征包 |
| POST | `/compare` | `files=` 多份 + `bidders=` 等长投标人名 + `project=` + `extra=`(JSON) |
| POST | `/report` | 同上入参 → 下载 Word 报告 |

`extra` 形如 `{"甲公司":{"upload_ip":"1.2.3.4","mac":"AC-DE-48-00-11-22"}}`。

## 边界与免责

- **只读**：不修改原件，逐份记录 MD5/SHA256 便于存证。
- **不读正文**：只解析容器与元数据；文本雷同比对属另一环节。
- **不下认定**：输出的是客观特征比对结果与处置建议。认定须由有权主体在听取投标人解释后依法作出。
  界面和 Word 报告里都印了这句话，对外出具时不要删。

## 运维

- 重建：`cd ~/platform && docker compose build bid-forensics && docker compose up -d bid-forensics`
- **坑**：构建容器无 DNS，Dockerfile 走清华源 + compose `build.network: host`，否则拉不到包。
- 上传上限 `FORENSICS_MAX_MB`（默认 200），网关 `client_max_body_size 200m` 要同步。
- 备份：接入时改动的四个文件均有 `.bak.forensics`（nginx.conf / PORTS.md / ops-console app.py 与 nav.html）。
